# GitLab — практический гайд

> Цель: поднять свой GitLab в HomeLab (Proxmox), подключить Runner, перенести CI/CD проекта PetWeb из GitHub Actions в GitLab CI и понять, как всё это устроено.
> Установка пакетом из репозитория описана в [Установка](#docs/GitLab/Установка.md) — здесь вариант через Docker и всё, что дальше.

---

## 0. Что такое GitLab и из чего он состоит

GitLab — это «всё в одном»: Git-хостинг, Merge Requests, Issues, CI/CD, Container Registry, Package Registry, Wiki, Pages.

| Компонент | Зачем |
|-----------|-------|
| **GitLab Rails (Puma)** | веб-интерфейс и API |
| **Gitaly** | хранение git-репозиториев |
| **PostgreSQL** | метаданные (пользователи, MR, пайплайны) |
| **Redis + Sidekiq** | очереди фоновых задач |
| **GitLab Runner** | отдельный агент, который *выполняет* задачи CI |
| **Container Registry** | хранилище Docker-образов |

Главное, что надо понять: **GitLab только планирует пайплайн, а выполняет его Runner** — на другой машине, в Docker или в Kubernetes.

📚 Документация: https://docs.gitlab.com/

## 1. Требования и подготовка VM в Proxmox

| Ресурс | Минимум | Комфортно |
|--------|---------|-----------|
| CPU | 4 vCPU | 4–8 vCPU |
| RAM | 4 ГБ (+ swap 4 ГБ) | 8 ГБ |
| Диск | 40 ГБ | 100 ГБ (образы registry растут быстро) |

1. Создай VM `gitlab` на Ubuntu Server 24.04 (cloud-init шаблон из роадмапа k8s подойдёт).
2. Выдай статический IP, например `192.168.1.50`.
3. Добавь DNS-запись `gitlab.chepykella.ru` (или запись в локальном DNS/OpenWRT).
4. Поставь Docker — см. [Docker](#docs/Linux/Docker.md).

## 2. Установка GitLab CE через Docker Compose

```bash
sudo mkdir -p /srv/gitlab && cd /srv/gitlab
```

`docker-compose.yml`:

```yaml
services:
  gitlab:
    image: gitlab/gitlab-ce:latest
    container_name: gitlab
    hostname: gitlab.chepykella.ru
    restart: unless-stopped
    shm_size: 256m
    environment:
      GITLAB_OMNIBUS_CONFIG: |
        external_url 'https://gitlab.chepykella.ru'
        gitlab_rails['gitlab_shell_ssh_port'] = 2224
        # если TLS терминирует внешний nginx — слушаем http внутри
        nginx['listen_port'] = 80
        nginx['listen_https'] = false
        # экономим память в HomeLab
        puma['worker_processes'] = 2
        sidekiq['concurrency'] = 10
        prometheus_monitoring['enable'] = false
        # Container Registry
        registry_external_url 'https://registry.chepykella.ru'
        registry_nginx['listen_port'] = 5050
        registry_nginx['listen_https'] = false
    ports:
      - "8929:80"     # web
      - "5050:5050"   # registry
      - "2224:22"     # ssh для git
    volumes:
      - ./config:/etc/gitlab
      - ./logs:/var/log/gitlab
      - ./data:/var/opt/gitlab
```

```bash
docker compose up -d
docker logs -f gitlab          # первый старт ~3–5 минут
docker exec -it gitlab grep 'Password:' /etc/gitlab/initial_root_password
```

Пароль из `initial_root_password` удаляется через 24 часа — сразу смени его.

### Проксирование через nginx PetWeb

В `nginx/nginx.conf` добавь server-блок (сертификат wildcard `*.chepykella.ru` уже подходит):

```nginx
server {
    listen 443 ssl;
    http2 on;
    server_name gitlab.chepykella.ru;

    ssl_certificate     /etc/letsencrypt/live/www.chepykella.ru/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/www.chepykella.ru/privkey.pem;

    client_max_body_size 512m;

    location / {
        proxy_pass http://192.168.1.50:8929;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto https;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
    }
}
```

📚 https://docs.gitlab.com/install/docker/

✅ **Задание 1.** Подними GitLab, зайди под root, смени пароль, отключи открытую регистрацию: *Admin → Settings → General → Sign-up restrictions*.

## 3. Первичная настройка

1. **Пользователь.** Создай обычного пользователя для себя, root используй только для админки.
2. **SSH-ключ.** *Preferences → SSH Keys* → вставь `~/.ssh/id_ed25519.pub`.
3. **2FA.** *Preferences → Account → Enable two-factor authentication*.
4. **Группа.** Создай группу `homelab` — переменные и раннеры, заданные на группе, наследуются всеми проектами.
5. **Защита main.** *Project → Settings → Repository → Protected branches*: push в `main` — только Maintainers, merge — через MR.

Клонирование через нестандартный порт SSH:

```bash
git clone ssh://git@gitlab.chepykella.ru:2224/homelab/petweb.git
```

✅ **Задание 2.** Создай группу `homelab`, проект `petweb`, запушь туда этот репозиторий:

```bash
git remote add gitlab ssh://git@gitlab.chepykella.ru:2224/homelab/petweb.git
git push gitlab main
```

## 4. GitLab Runner

Runner — отдельный процесс, который забирает задачи и выполняет их через **executor**:

| Executor | Когда использовать |
|----------|-------------------|
| `docker` | 95% случаев: каждая задача в чистом контейнере |
| `shell` | задачи прямо на хосте (деплой на эту же машину) |
| `kubernetes` | задачи — поды в кластере (после роадмапа k8s) |

### Установка Runner в Docker

```bash
docker run -d --name gitlab-runner --restart unless-stopped \
  -v /srv/gitlab-runner/config:/etc/gitlab-runner \
  -v /var/run/docker.sock:/var/run/docker.sock \
  gitlab/gitlab-runner:latest
```

### Регистрация (новый способ — через authentication token)

1. *Project (или Group) → Settings → CI/CD → Runners → New project runner*.
2. Укажи теги, например `docker,homelab`, нажми **Create runner** — получишь токен `glrt-...`.
3. Зарегистрируй:

```bash
docker exec -it gitlab-runner gitlab-runner register \
  --non-interactive \
  --url "https://gitlab.chepykella.ru" \
  --token "glrt-XXXXXXXXXXXXXXXX" \
  --executor "docker" \
  --docker-image "alpine:3.20" \
  --docker-privileged \
  --description "homelab-docker"
```

`--docker-privileged` нужен для сборки образов через `docker:dind`. Альтернатива без привилегий — Kaniko или Buildah.

📚 https://docs.gitlab.com/runner/register/

✅ **Задание 3.** Зарегистрируй раннер, убедись, что он зелёный в *Settings → CI/CD → Runners*.

## 5. Синтаксис `.gitlab-ci.yml`

Минимальный пайплайн:

```yaml
stages: [build, test, deploy]

build:
  stage: build
  image: node:20-alpine
  script:
    - npm ci
    - npm run build
  artifacts:
    paths: [dist/]
    expire_in: 1 week

test:
  stage: test
  image: node:20-alpine
  script:
    - npm test

deploy:
  stage: deploy
  script: ./deploy.sh
  environment: production
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
```

### Ключевые слова, которые нужно знать

| Ключ | Что делает |
|------|-----------|
| `stages` | порядок этапов; задачи одного этапа идут параллельно |
| `image` / `services` | образ задачи и сопутствующие контейнеры (`docker:dind`, `postgres`) |
| `script`, `before_script`, `after_script` | команды |
| `rules` | когда запускать задачу (заменяет устаревшие `only/except`) |
| `needs` | DAG: запуск сразу после указанных задач, не дожидаясь этапа |
| `artifacts` | файлы, передаваемые между задачами / доступные для скачивания |
| `cache` | кэш между пайплайнами (`node_modules`, `.m2`) |
| `variables` | переменные задачи / пайплайна |
| `environment` | окружение (история деплоев, кнопка Rollback) |
| `resource_group` | запрет параллельных деплоев |
| `when: manual` | ручной запуск (кнопка ▶) |
| `include` | подключение шаблонов из других файлов/проектов |
| `extends` / якоря `&`/`*` | переиспользование кусков конфигурации |
| `tags` | выбор раннера |

### Полезные предопределённые переменные

`$CI_COMMIT_SHA`, `$CI_COMMIT_SHORT_SHA`, `$CI_COMMIT_BRANCH`, `$CI_DEFAULT_BRANCH`, `$CI_PIPELINE_SOURCE`, `$CI_REGISTRY`, `$CI_REGISTRY_IMAGE`, `$CI_REGISTRY_USER`, `$CI_JOB_TOKEN`.

📚 Справочник: https://docs.gitlab.com/ci/yaml/
📚 Переменные: https://docs.gitlab.com/ci/variables/predefined_variables/

✅ **Задание 4.** Сделай пайплайн из трёх задач, где `test` использует `needs`, а `deploy` запускается только вручную (`when: manual`) и только из `main`.

## 6. Переменные и секреты

*Settings → CI/CD → Variables*:

| Флаг | Значение |
|------|----------|
| **Protected** | доступна только в защищённых ветках/тегах |
| **Masked** | значение скрывается в логах |
| **Expand** | раскрывать `$` внутри значения |
| **Type: File** | GitLab кладёт значение во временный файл, в переменной — путь к нему |

Для SSH-ключа и многострочных секретов используй **Type: File** — так не придётся бороться с переносами строк:

```yaml
before_script:
  - cp "$SSH_PRIVATE_KEY" ~/.ssh/id_deploy && chmod 600 ~/.ssh/id_deploy
```

⚠️ Никогда не коммить пароли в `docker-compose.yml` — бери их из переменных (`${GRAFANA_ADMIN_PASSWORD}`), а `.env` генерируй в CI.

## 7. Container Registry

```yaml
build-image:
  stage: build
  image: docker:27
  services: [docker:27-dind]
  variables:
    DOCKER_TLS_CERTDIR: "/certs"
  script:
    - docker login -u "$CI_REGISTRY_USER" -p "$CI_REGISTRY_PASSWORD" "$CI_REGISTRY"
    - docker build -t "$CI_REGISTRY_IMAGE/bot:$CI_COMMIT_SHORT_SHA" ./bot
    - docker push "$CI_REGISTRY_IMAGE/bot:$CI_COMMIT_SHORT_SHA"
```

На сервере тянем уже готовый образ, а не собираем — деплой быстрее и воспроизводим.

📚 https://docs.gitlab.com/user/packages/container_registry/

## 8. CI/CD проекта PetWeb в GitLab

В корне репозитория уже лежит [`.gitlab-ci.yml`](https://github.com/4pykella/PetWeb/blob/main/.gitlab-ci.yml) — полный аналог GitHub Actions:

```
validate ─┐
          ├─► deploy (только main, resource_group: production)
docker-build ┘
```

1. **validate** — генерирует `html/miki/files.json`, проверяет синтаксис бота.
2. **docker-build** — `docker compose config` и сборка образов `nginx` и `workdays-bot` в `docker:dind`.
3. **deploy** — собирает `.env` и `secrets/acme.env` из переменных, заливает архив по SSH в `/opt/petweb` и запускает `scripts/deploy.sh`, который:
   - выпускает wildcard-сертификат `*.chepykella.ru` по DNS-01 через `acme.sh` (`cert.sh auto`);
   - если ключей DNS нет или выпуск упал — **деплой продолжается**: остаётся старый сертификат, либо nginx генерирует самоподписанный;
   - делает `docker compose up -d --build` и health-check.

### Переменные, которые нужно завести

| Переменная | Тип | Пример |
|------------|-----|--------|
| `SSH_PRIVATE_KEY` | File, Protected | содержимое `~/.ssh/id_ed25519` деплой-пользователя |
| `SSH_HOST` | Variable | `185.x.x.x` |
| `SSH_USER` | Variable | `deploy` |
| `SSH_PORT` | Variable | `22` (опционально) |
| `BOT_TOKEN` | Masked, Protected | токен от @BotFather |
| `BOT_ADMIN_IDS` | Variable | `123456789` |
| `GRAFANA_ADMIN_PASSWORD` | Masked | |
| `CODE_SERVER_PASSWORD` | Masked | |
| `ACME_EMAIL` | Variable | почта для Let's Encrypt |
| `ACME_DNS_PROVIDER` | Variable | `dns_selectel` / `dns_regru` / `dns_cf` |
| `ACME_DNS_ENV` | File, Protected | ключи API провайдера, см. ниже |

Пример `ACME_DNS_ENV` для Selectel (API v2, сервисный пользователь с ролью на DNS):

```
SL_Ver=v2
SL_Expire=60
SL_Login_Name=dns-bot
SL_Login_ID=123456
SL_Project_Name=my-project
SL_Pswd=********
```

Для reg.ru: `REGRU_API_Username=...` и `REGRU_API_Password=...`, для Cloudflare: `CF_Token=...`. Полный список: https://github.com/acmesh-official/acme.sh/wiki/dnsapi

### Подготовка сервера

```bash
sudo adduser --disabled-password deploy
sudo usermod -aG docker deploy
sudo mkdir -p /opt/petweb && sudo chown deploy: /opt/petweb
# на своей машине
ssh-keygen -t ed25519 -f ~/.ssh/petweb_deploy -N ""
ssh-copy-id -i ~/.ssh/petweb_deploy.pub deploy@SERVER
```

## 9. Зеркалирование GitHub ↔ GitLab

Чтобы не выбирать, где жить коду:

- **Pull mirror** (GitLab тянет из GitHub): *Settings → Repository → Mirroring repositories*, направление *Pull* (в CE доступно только для публичных проектов через импорт; для приватного — push mirror со стороны GitHub Actions).
- **Push mirror** (GitLab пушит в GitHub): там же, направление *Push*, пароль — GitHub PAT с правом `repo`.

Тогда коммит в любой из них запустит пайплайн в обоих местах — **отключи деплой в одном**, чтобы не деплоить дважды.

## 10. Обслуживание

```bash
# бэкап (данные + репозитории)
docker exec -t gitlab gitlab-backup create
# конфиги и секреты бэкапятся отдельно!

# проверка состояния

docker exec -it gitlab gitlab-ctl status

# https://docs.gitlab.com/update/upgrade_paths/
docker compose pull && docker compose up -d
```

Чистка registry от старых тегов — *Settings → Packages and registries → Cleanup policies*.

## 11. Траблшутинг

| Симптом | Причина / решение |
|---------|-------------------|
| `502 Whoops, GitLab is taking too much time` | ещё стартует или не хватает RAM → добавь swap / память |
| Job висит в `pending` | нет раннера с нужными `tags` или раннер offline |
| `Cannot connect to the Docker daemon` в dind | раннер без `--docker-privileged` или не задан `DOCKER_TLS_CERTDIR` |
| `Host key verification failed` при деплое | не выполнен `ssh-keyscan` / сменился ключ сервера |
| `Permission denied (publickey)` | публичный ключ не в `~deploy/.ssh/authorized_keys` |
| Переменная пустая в job | она *Protected*, а ветка — нет |
| SSL не выпустился | смотри лог шага `[2/5] SSL certificate`, проверь `ACME_DNS_ENV` |
